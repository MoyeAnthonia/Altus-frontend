Altus Frontend | MediaPipe Architecture

How the camera, Pose model, and game engine actually connect

This page is the fast version of the markdown walkthrough. It shows the real runtime path, the event handoff between modules, and the reason the camera used to stay on after back navigation.

1. Camera starts

`getUserMedia` opens a hidden webcam stream for detection.

2. Pose runs per frame

`requestAnimationFrame` drives `detectForVideo(...)` continuously.

3. Detectors interpret

Squat and arm logic listen to raw landmarks and add meaning.

4. Game reacts

The engine listens to named events only: no direct camera access.

End-to-end flow

Camera permission Browser asks for webcam access with `getUserMedia`.
->
Hidden video element `mediapipePlayer.tsx` keeps the camera stream off-screen.
->
Pose inference MediaPipe reads one frame at a time and returns landmarks.
->
Raw event `mv:pose` broadcasts the landmark data to any listener.
Squat detector Hip baseline + 3-frame confirmation + cooldown.
->
Arm gesture detector Wrist above shoulder becomes confirm or cancel.
->
Game engine Listens for `mv:squat:start`, `mv:confirm`, `mv:cancel`.
->
State change Calibrate, jump, restart, or exit depending on state.

What runs every frame

Loop driver

requestAnimationFrame

Typical cadence

About 60 FPS

Model call

detectForVideo(...)

The model is not polled once per second. It is called on every animation frame, so the real speed depends on browser repaint rate, device performance, and how expensive the model inference is on that machine.

What stops the camera

1. `stopMediaPipe()` cancels the animation frame Stops the per-frame loop so the model does not keep running.
2. It stops every MediaStream track Releases webcam hardware access with `track.stop()`.
3. It closes the Pose landmarker Frees the WASM/GPU resources used by MediaPipe.
4. It removes the hidden video element The camera lifetime is ended in module cleanup, not by React alone.

The bug before the fix

problem two streams

The back button used to leave the webcam on because there were two independent camera lifetimes:

Hidden MediaPipe stream Owned by `mediapipePlayer.tsx` and cleaned up by `useMediaPipe()`.
Visible preview stream Owned by `Exercise.tsx` so the user could see the live camera card.

The fix

solution explicit teardown

The cleanup was made explicit in both places, so navigation away from the page now releases the webcam correctly.

`useMediaPipe()` cleanup Removes listeners and calls `stopArmGestureDetector()`, `stopSquatDetector()`, and `stopMediaPipe()`.
`Exercise.tsx` cleanup Stops the preview stream by calling `streamRef.current?.getTracks().forEach(track => track.stop())`.

Useful file map

  • src/mediapipe/mediapipePlayer.tsx starts the camera, loads the model, and emits mv:pose.
  • src/mediapipe/squatDetector.tsx turns landmarks into calibration and squat events.
  • src/mediapipe/armGestureDetector.tsx turns landmarks into confirm and cancel gestures.
  • src/mediapipe/useMediaPipe.tsx owns the startup and cleanup lifecycle.
  • src/pages/Exercise/Exercise.tsx manages the visible preview stream.
  • src/engine/DinoRunGameEngine.ts reacts to the named events and changes game state.
